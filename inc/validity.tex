The whole thesis rests on one comparison. The agentic system and the workflow
baseline run the same evacuation, and we set their results side by side. That
comparison only means something if the two systems work under the same
conditions. If one of them sees more of the world, can say more to it, or is
scored in a different way, then the result tells us about the test rig and
little about the architecture.

In this chapter we show where the conditions are the same and where they
differ. We do not rely on prose for this. Parity is built into the code and
checked by an executable test suite. Where the two systems differ on purpose,
we give each difference together with the direction in which it pushes the
result. The chapter comes before the results because the results can only be
read once this is settled.

\section{What Parity Has to Mean Here}
\label{sec:val:definition}
% source: PARITY sec.0, sec.6

The study has one independent variable, which is how coordination is
produced. On the treatment side, coordination comes from distributed LLM
agents. Each holds local information and negotiates through the shared
database. On the control side, one deterministic Incident Commander (IC)
follows written doctrine. Everything else has to be the same.

The comparison is therefore narrower than ``LLM against no LLM''. The IC
replaces only the two coordination agents that reason with a model: the
command post (BIS) and the transport dispatcher (Hochbahn). The bus drivers and
the other field agents still run a language model in both conditions.
Section~\ref{sec:val:scope} gives the full roster.

\paragraph{Parity by identity.} A common way to build a fair control is to
write a second system that behaves like the first. The weakness of that
approach is drift. A copy can match the original today and differ from it
tomorrow without anyone noticing. We used a stricter rule. The IC is built on
the same engine that all ten agents run on, and it reuses the code of the two
agents it replaces as the very same functions in memory.

Every attribute the IC defines falls into one of three groups. It defines 49.
Of these, 27 are the unmodified functions of the two absorbed agents, 23 from
BIS and 4 from Hochbahn. The other 22 are new code, and each comes with a
written reason. Some merge two versions, because both agents defined the same
function and the IC needs one. One is the seam where the independent variable
sits. The rest belong to the message link between the two agents, which
disappears once they become one node. Anything the IC does not define itself
comes unchanged from the shared engine. The test compares identity, so a
reimplementation fails it even if it behaves the same. A new method with no
written reason also fails.

The IC keeps one flat state that holds every field of both agents' states.
Nesting the two states would split the command lifecycle, the inbox and the
event log in two, and the reused functions need a single copy of each. The
test checks that every field keeps its name, type and default.

\paragraph{What identity cannot show.} Because the IC can issue more commands
than either agent alone, we cannot replay an IC run through one of the original
agents. That agent would drop the commands it does not know, and the two logs
would differ for reasons that have nothing to do with parity. Three of the five
axes below are therefore checked structurally. The test shows that both sides
run the same code, but it does not observe them behaving alike on a sample
run. The structural claim is the stronger one, since it holds for every
scenario. What we lose is a concrete side-by-side trace that a reader can
inspect.

For each axis it names what the two systems share, how that sharing is held and

\paragraph{Information horizon.} Both sides receive the same messages at the
same simulation time, and both read the world through the same sensing
functions. The test walks a scenario and checks three things. The inbox holds
the messages the turns delivered and nothing more. Every sender is a known
party. Both snapshots come from the shared sensing code. One real difference
remains. On the agentic side, the command picture and the fleet picture live
in two agents, which have to message each other to combine them. The IC holds
both at the same time. It therefore sees more in one place, but every fact it
sees arrived by a route the agents also have. This is deviation~5 in
Section~\ref{sec:val:deviations}.

\paragraph{Action vocabulary.} BIS has 11 coordination commands and Hochbahn
has 7. They share one, so together they have 17. Merging the two agents removes
the link between them, and four commands exist only for that link: asking for
a deadline extension, reporting a finished transport, waiting for transport,
and requesting buses. Under central command the transport section and the
commander are the same authority, so there is nobody to negotiate with. The IC
therefore has 13 commands. We state this consequence before the results: the
agentic system can hold an extension negotiation and the baseline cannot. Any
metric that rewarded such a negotiation would score a link that only one
architecture has.

The test requires the IC's command set to equal this union. A subset check
would not be enough, since a command missing from the control is as much a gap
as an extra one. The IC holds no physical commands. Driving stays with the
driver agents in both conditions.

Both sides have the same commands available, but they do not use all of them.
The baseline's procedure issues 9 of its 13. The four it never issues are two
commands that end the mission, one that stands the escorts down for good, and a
free-text message channel that a fixed procedure has no use for. A test fails
if this gap ever grows. A last check reads the text of the agentic prompts. A
worked example in a prompt could teach a model a command the baseline lacks,
and the sweep found no such example.

\paragraph{World model.} Each absorbed agent reads the world in one place only,
and the IC calls those two functions and no others. The shared sensing back
ends are set up the same way and stay in place for the whole run. When an
action is committed, both sides run the same timing and feasibility pass,
because it is the same inherited method. One difference is new with the IC.
Its run schedule reads real road distance and duration from the routing
service. The agentic coordinator never sees these numbers; only the drivers do.
This is deviation~6. It enters the IC's planning and leaves the commit step,
which this axis is about, unchanged. The road data is cached on disk, and a
cache miss falls back to a fixed straight-line estimate, so baseline runs stay
reproducible.

\paragraph{Scenario inputs.} Both sides load every scenario file through the
same function, and the test runs it over all 15 files. Two details of the
message envelope differ (deviations~1 and~2), and neither reaches a decision.
One paired scenario has a different head-count on purpose. In the road-closure
scenario, the agentic side can re-route. The closure then costs time and
distance, both shelters stay reachable, and all 100 residents can be placed.
The baseline has no routing command, so the only way to express a closure to
it is as a shelter that can no longer be reached. Losing a 60-bed shelter would
leave 40 residents without a bed, so the baseline file holds 60 residents. The
comparison stays fair because we score completeness against each scenario's
own declared population. Everything else that frames the score, such as the
hazard zone, the flood arrival and the fleet, is asserted identical. A test
makes sure that this is the only scenario with a population other than 100.

\paragraph{Output substrate.} Both sides write the same seven-field rows into
the same append-only \code{event_log}, and the same inherited code writes them.
The test checks that the event numbers have no gaps across a whole run, since a
gap would point to a second writer or a lost row. Two labels differ on purpose.
A baseline decision row is labelled ``decision'' instead of ``LLM response'',
and its model name is empty. Logging a decision that used no model as an LLM
response is the kind of quiet mislabelling the shared log is meant to prevent.
The test shows that the label does no harm. If every baseline decision row is
relabelled, the facts the scorer extracts stay byte-identical.

\section{Scope of the Independent Variable}
\label{sec:val:scope}

all others in place. Table~\ref{tab:val:roster} shows how the ten agents split.

The eight agents that stay are identical in both conditions by construction,
which puts them outside the comparison. The four scripted agents are already
deterministic, so moving them would change no variable. The four field agents
stay because driving a route is the same act under either architecture. Leaving
them untouched gives a stronger guarantee than auditing a replacement would.

The result should be read with this scope in mind. The independent variable is
how coordination is produced. One side has a deterministic command cycle that
holds every coordination function. The other has distributed LLM agents that
each hold local information. Language models run on both sides.

Because the IC absorbs both coordination agents, the baseline plans its own
evacuation. It writes a run schedule with a passenger split, per-run deadlines
and a delivery estimate that can be checked against the outcome. Whether the
baseline is a competent command system is therefore something we can test.
The design record for the IC contains a rule that the reserve bus should only
be used in sequential runs. The code does not follow that rule, and we make no
claim that relies on it. Section~\ref{sec:val:reserve} describes what the code
does.

\paragraph{Deviations 1 to 4 are inert.} Each one serves honest logging or
determinism, and none can reach a decision or a score. Each has its own test.
The message id is a good example. It is replaced by a fresh one as soon as a
message enters an inbox, so it never reaches the situation picture, a prompt
or a decision.

\paragraph{Deviations 5 and 6 favour the control.} Both follow from the
doctrine. A central commander who could not see what they command would be a
strawman, and a schedule measured in minutes needs travel times. We accepted
both for these reasons and report them instead of correcting them. They cost
the agentic side, and they have to be read in both directions. Had the agentic
system won despite them, the win would have counted for more, because
distributed reasoning would have beaten a commander with a better view. Since
the agentic system lost, part of the gap may come from the wider view rather
than from the coordination procedure itself.

\paragraph{Deviation 7 runs the other way.} Only the baseline's scenario files
declare a world, which a small simulator plays out. The agentic files have no
such block. This takes an advantage away from the control rather than giving it
one. The campaign ran with this asymmetry in place, and the next section
explains why it does not threaten the result.

\section{Deviation 7 and Why It Does Not Threaten the Result}
\label{sec:val:dev7}
% source: PARITY sec.4e; RESULTS sec.6.8 item 1; THESIS_SOURCES sec.4 item 3

The evaluation protocol set a gate before any confirmatory claim: deviation~7
had to be ``closed, or re-argued in writing''. We discharge the gate by
argument.

The argument turns on what the deviation removes. Without a declared world, a
baseline scenario injected fixed drop-off confirmations. The same messages
arrived at the same times and named the same shelters, whatever the doctrine
had decided. The scorer never read where the residents were actually sent, so
a baseline that sent everyone to a closed shelter would still have scored full
completeness. In that setup the control's outcome was written into the script
instead of being earned in the run. The agentic side never had this help,
because its counterparties are live agents. Declaring a world on the baseline
side removes the help, so the deviation works against the baseline.

This direction settles the matter for our result, which is that the baseline
won. A deviation that puts the baseline at a disadvantage cannot explain a
baseline win. If it had any effect, it made the baseline's margin look smaller
than it is.

We note that the argument depends on which side won. Had the agentic system
won, we would first have had to close the gate properly, by giving the agentic
scenarios the same world. As it stands, deviation~7 is an open asymmetry whose
direction is opposed to the result, and so it does not threaten it.

\section{Two Further Asymmetries Outside the Numbered Seven}
\label{sec:val:extra}
% source: PARITY sec.3d (residual) and audit item 5; RESULTS sec.6.7

Two more differences are not among the seven. Both favour the baseline, and
both also appear in the limitations.

\paragraph{Where a replacement bus leg starts.} Both sides measure bus
kilometres by the same rule. A leg is charged once, when the bus starts it,
from where the bus stands. The two sides differ in how they know where the bus
stands. An agentic driver's next leg starts from its real position, which the
world reports back. The baseline has no live position to read, so it places the
bus at the destination it was heading for. That is the cheaper of the two
possible starting points, which favours the baseline. We measured the gap on
three scenarios: 83.1\,km against 89.1\,km on the baseline road closure, 99.2
against 105.2 on shelter capacity, and 92.8 against 95.8 on bus breakdown. The
gap is at most 6\,km, and no level changes anywhere in that range. Closing it
would need a position model for the control, with no runtime to feed it, so we
report the gap and leave it open.

\paragraph{A fallback prompt that mis-frames two message types.} The command
post picks a short instruction block, a playbook, for each kind of incoming
message. It has no playbook for a route update or a bus breakdown. Both fall to
the fallback, which is meant for messages the runtime could not classify, and
whose instruction is to assume the resource will not come. The baseline handles
both disruptions with written branches. This weakens the agentic side and makes
the comparison on the road-closure scenario (S02) unfair in the baseline's
favour. We report it as a limitation of that comparison. Its reach is smaller
than it first appears. The agentic road-closure scenario delivers the closure
to the transport dispatcher as a situation update, and situation updates have
their own playbook. We have not established whether the command post met a
route update in any scored run.

\paragraph{Taken together.} Deviations~5 and~6 and these two items all favour
the baseline. They may account for part of the margin, but they cannot reverse
the result or explain the agentic deficit away. The one asymmetry that works
against the baseline, deviation~7, could only have made the margin look
smaller.

\section{The Reserve-Bus Mechanism}
\label{sec:val:reserve}
% source: PARITY reserve-bus box; ADR-0017 sec.1; THESIS_SOURCES sec.4 item 2
% A NAMED MECHANISM, NOT A CONFOUND (decision of 2026-09-06).

One difference between the two systems looks like a deviation at first sight
but is a difference in decisions.

Every scenario marks the second bus as a reserve with 50 seats. The baseline's
scheduler never reads that role. It gives each leg to the bus that is free
first, so the second leg goes to bus~2 at the start and the two buses run in
parallel. The agentic transport dispatcher reads the role and keeps bus~2
parked by default. It releases the bus for one of four reasons: a load larger
than bus~1 can carry, bus~1 being unavailable, the command post asking for two
buses, or a deadline test that fails when the last delivery would land less
than 30 minutes before the mission deadline. Otherwise it runs bus~1 in serial
trips.

We treat the reserve role as soft. A reserve exists to be used when residents
would otherwise drown. Both sides have the same fleet, and both may send bus~2.
Sending it at once and keeping it parked are two choices over the same
capability, and choices are what the comparison measures. We therefore do not
count this among the deviations. When the agentic side leaves the reserve
parked while residents are at risk, we report it as a failure of decision
quality on that side. It is one of the named mechanisms behind the gap.

\section{How Parity Is Verified}
\label{sec:val:verification}
% source: PARITY "On test strength", "Verification"; workflow-baseline-README l.33

Every claim in this chapter is backed by an executable test. The parity suite
has 17 test functions, which expand to 31 test items, and it needs neither a
database nor a model. The baseline package as a whole carries 160 test items.
One test ties the audit to the code in both directions. Every parity test must
be cited by a row of the capability table, and every row must cite a test that
exists.

The suite also guards against tests that pass because there is nothing to
check. A test such as ``every reused function is the original'' would pass on
an empty list. Each key assertion therefore comes with a check that its subject
is present, for example that at least one absorbed function is reached and that
each prompt module teaches at least five commands.

The verification has three limits.

\begin{itemize}
\item \textbf{The parity tests were not mutation-tested.} A mutation test breaks
  the code on purpose and confirms that a test fails. The audit specifies a
  minimum set of nine such mutations for the parity tests, and they were not
  run before the freeze of 2026-09-10.
\item \textbf{The gate followed the change it guards.} The design record asked
  for the parity gate to be written, and to fail, before the engine changed.
  The engine changed first, so for a short time the audit did not cover it.
\item \textbf{One entry in the list of new IC code is redundant.} The list has
  23 entries for 22 new attributes, because one listed function is in fact
  reused by identity. This has no effect, since the test checks reuse first.
\end{itemize}

\paragraph{What the results may claim.} The two systems share their world,
their inputs, their commands and their output substrate. Most of that sharing
is shown by identical code, and the rest by tests on behaviour. Where the
systems differ, we give the direction of each difference. The differences that
can matter favour the baseline, and the one that does not could only have
hidden part of its margin. The results in Chapter~\ref{ch:results} can
therefore be read as a comparison of two ways of coordinating. Because
deviations~5 and~6 give the control a wider view by design, they do not
isolate the coordination procedure on its own.
