RQ3 asks what would have to change, and what a designer should consider, when
building an agentic simulation for emergency coordination. We answer it with
four groups of considerations. Each one comes from a measurement in this study
and comes with its limit. The evidence is argued in
Chapters~\ref{ch:results} to~\ref{ch:discussion}.

\section{Agent Architecture: Commit, Then Confirm}
\label{sec:design:commitment}
\label{sec:design:closure}

Our agentic architecture re-plans when a disruption arrives, so a designer
also has to decide what stops a re-plan. Our system already limits when the model is called. It wakes
only for a message, a finished step or a timing conflict, and a splice keeps
every action already sent to the world (Section~\ref{sec:ag:replan}). It does
not limit what a wake may change. On any wake the model may supersede a step
whose actions are already on the road, and the old step is then aborted with
no reason required. In our runs, the more often a run revised its plan, the
less it delivered. Full delivery fell from 90\% at the minimum number of
revisions to 32\% at six or more (Figure~\ref{fig:res:commitment}).

We therefore suggest a commitment boundary on the supersede. In the terms of
\textcite{cohen1990}, an agent should keep an intention until it has a reason
to drop it. A leg in flight stays committed unless the agent states why it
must be cancelled, and the runtime records that reason and counts it against a
limit. A new message can still wake the agent and change the steps that are
waiting. Cancelling a leg on the road becomes a separate, explicit act with a
cost.

The coordinator also needs a reliable way to learn that a leg is done. Our
message layer worked well, and residents were lost all the same
(Section~\ref{sec:disc:mechanism}). One abort text reads ``plan revision 2
claimed both runs drop off by 10:50, but no \code{transport_complete}
arrived''. A coordinator that cannot tell whether a leg has finished may
re-plan a leg that succeeded, or give up on one that is still running. A
designer should therefore give every
leg an explicit delivery confirmation and measure delivery directly.

The limit is the causal direction. A failing run may re-plan because it is
failing, so the case for the boundary rests on an association. A
commitment-constrained variant would show whether it is also the cause
(Section~\ref{sec:concl:future}).

\section{Scenario Design: Make the Problem Real}
\label{sec:design:binding}
\label{sec:design:reserve}

We sized the case so that the allocation binds: 100 residents, two buses with 50 seats each and two
shelters with 60 beds each (Chapter~\ref{ch:casestudy}). No bus can carry
everyone in one trip, and no shelter can take everyone. With slack resources
any plan works, and coordination goes untested.

Binding resources are not enough on their own. In our scenarios every
disruption arrived as a message and left the declared world unchanged. When
SC1 was reported to have only 40 beds, it still declared 60, so a plan that
ignored the report was never penalised. A disruption should change the state
that the scorer reads. A shelter with fewer beds should then hold fewer
residents in the simulation, and a plan that ignores the change should fail.
Deliveries should also be earned in the simulation, so that a wrong plan shows
up as a lower score.

The same care applies to every meaning a scenario declares. Our scenarios
mark the second bus as a reserve, which the agentic dispatcher obeys and the
baseline's scheduler never reads. We decided after the fact to read this as a
difference in decisions (Section~\ref{sec:wf:fleet}). A designer should fix
such meanings in advance. Either the shared substrate enforces them for both systems, or the
gap is listed as a deviation together with the side it favours.

\section{Evaluation Design: Test the Test First}
\label{sec:design:gate0}
\label{sec:design:variance}

A scenario only tests a disruption if a system that ignores it scores worse
than one that responds. A no-replan control \parencite{lipsitch2010}
checks this at two runs per scenario (our novel arm fails it,
Section~\ref{sec:crit:gate0}). Gate~0 should run before any campaign starts.

\begin{itemize}
\item \textbf{Size the design before the runs.} A sign test over five
  scenarios cannot reach significance, whatever the data
  (Section~\ref{sec:crit:power}), so it needs more scenarios. For the risk difference, state the smallest effect the design can
  detect \parencite{cohen1988}, and raise $k$ or drop the claim before data
  collection.
\item \textbf{Fix the models in advance.} Our third model slot changed after
  data were seen, and each such choice opens a path the analysis could have
  taken differently \parencite{gelman2014}. Choose all models and a
  replacement rule before the first run, and pin each model version.
\item \textbf{Treat retries as a factor.} Our system does not retry malformed
  model output. A retry would give a weak model a second attempt that a strong
  model never needed, and it would change what is measured.
\end{itemize}

Unlike the baseline, the agentic side is not deterministic
\parencite{yuan2025}. An evaluation should report its variance across runs next
to the mean.

\section{Cost, and the Limits of These Considerations}
\label{sec:design:cost}
\label{sec:design:scope}

An agentic architecture is costly by design. Ours needed nine to ten
times the baseline's messages per resident delivered, and most of its runs
overran the time budget (Section~\ref{sec:res:responsetime}).
A designer should plan this cost from the start and decide what it has to buy.
Other work finds that one strong agent with good prompts can match a
multi-agent discussion \parencite{wang2024}. Whether the cost pays off on a
scenario that passes Gate~0 is untested. These considerations come from one evaluation of one architecture on one case
(Section~\ref{sec:crit:limitations}). They should be tested on the next design
in this space before they are generalised.
