RQ3 asks what would have to change, and what a designer should consider, when
building an agentic simulation for emergency coordination. In this chapter we
answer it with four groups of considerations. Each one comes from a measurement in this study, and each one
has a limit that we state with it. The evidence is argued in
Chapters~\ref{ch:results} and~\ref{ch:critique}, so here we only point to it.

\section{Agent Architecture: Commit, Then Confirm}
\label{sec:design:commitment}
\label{sec:design:closure}

The main feature of our agentic architecture is that it re-plans when a
disruption arrives. A designer who builds this in also has to decide what
stops a re-plan. Our system already limits when the model is called. It wakes
only for a message, a finished step or a timing conflict, and a splice keeps
every action already sent to the world (Section~\ref{sec:ag:replan}). It does
not limit what a wake may change. Every new message is a wake, and on any wake
the model may supersede a step whose actions are already on the road. The old
step is then aborted, with no reason required. On our scenarios the right number of re-plans was zero. Runs that kept
to the minimum of two plan revisions delivered every resident in 90\% of
cases. Runs with six or more revisions did so in 32\% of cases
(Figure~\ref{fig:res:commitment}). The number of revisions correlates with
survival at $r = -0.408$, while the number of dispatched missions hardly
matters ($r = -0.070$).

We therefore suggest a commitment boundary on the supersede. A leg in flight
stays committed unless the agent states why it must be cancelled, and the
runtime records that reason and counts it against a limit. A new message can
still wake the agent and change the steps that are waiting. Cancelling a leg
on the road becomes a separate, explicit act with a cost.

A second point concerns how the coordinator learns that a leg is done. Our
message layer worked well. Over 1,932 addressed requests, 93.8\% of the
handshakes were closed (Section~\ref{sec:res:loss:handshakes}). Residents were
lost all the same. The coordinator's own abort texts show why. One reads
``plan revision 2 claimed both runs drop off by 10:50, but no
\code{transport_complete} arrived''. A coordinator that cannot tell whether a
leg has finished may re-plan a leg that succeeded, or give up on one that is
still running. Message health is a useful metric, but it does not show that
the job was done. A designer should give every leg an explicit delivery
confirmation and measure delivery directly.

The limit is the causal direction. Of the 108 aborts, 53\% are stand-downs
after a failure and only 13\% start from a re-plan. A failing run may
therefore re-plan because it is failing. The commitment boundary is supported
by a strong correlation. A commitment-constrained variant of the system would
show whether it is also the cause (Section~\ref{sec:crit:mechanism}).

\section{Scenario Design: Make the Problem Real}
\label{sec:design:binding}
\label{sec:design:reserve}

A coordination test needs something to coordinate. We sized the case so that
the allocation binds: 100 residents, two buses with 50 seats each and two
shelters with 60 beds each (Chapter~\ref{ch:casestudy}). No bus can carry
everyone in one trip, and no shelter can take everyone. With slack resources
any plan works, and the simulation then says little about coordination.

Binding resources are not enough on their own. In our scenarios every
disruption arrived as a message and left the declared world unchanged. When
SC1 was reported to have only 40 beds, it still declared 60, so a plan that
ignored the report was never penalised. A disruption should change the state
that the scorer reads. A shelter with fewer beds should then hold fewer
residents in the simulation, and a plan that ignores the change should fail. The scenario should also declare a
world in which deliveries are earned by the simulation, so that a wrong plan
can show up as a lower score.

The same care applies to every meaning a scenario declares. Our scenarios
mark the second bus as a reserve. The agentic dispatcher reads that role and
keeps the bus parked by default. The baseline's scheduler never reads it and
sends both buses at the start. We decided after the fact to treat the role as
soft and to read the difference as a difference in decisions
(Section~\ref{sec:wf:fleet}). A designer should fix such meanings in
advance. Either the shared substrate enforces them for both systems, or the
gap is listed as a deviation together with the side it favours.

\section{Evaluation Design: Test the Test First}
\label{sec:design:gate0}
\label{sec:design:variance}

A disruption scenario is only a disruption if a system that ignores it scores
worse than a system that responds. This can be checked cheaply with a
no-replan control, at two runs per scenario. We did not require this check on
the scored files. On all five novel scenarios the control committed
byte-identical orders and scored the identical level, so the novel arm could
not test adaptability at all (Section~\ref{sec:crit:gate0}). Gate~0 should run
before any campaign is spent on a scenario.

The campaign also taught us three smaller things about evaluation design.

\begin{itemize}
\item \textbf{Size the design before the runs.} At $k = 10$ over five
  scenarios, our registered sign test could not return $p$ below 0.0625,
  whatever the data (Section~\ref{sec:crit:power}). State the smallest effect
  the design can detect, and raise $k$ or drop the claim before data
  collection.
\item \textbf{Fix the models in advance.} The third model of the novel arm
  changed four times after data were seen. Each such choice opens a path the
  analysis could have taken differently \parencite{gelman2014}. Choose all models and a replacement
  rule before the first run, and pin each model version. Our cloud model tags
  are not version-frozen, so no digest pins our results.
\item \textbf{Treat retries as a factor.} Our system does not retry malformed
  model output. A retry would give a weak model a second attempt that a strong
  model never needed, and it would change what is measured.
\end{itemize}

The agentic side is also not deterministic \parencite{yuan2025}, while the
baseline is. Its
variance across runs is a real cost of the approach, and an evaluation should
report it next to the mean.

\section{Cost, and the Limits of These Considerations}
\label{sec:design:cost}
\label{sec:design:scope}

The cost of an agentic architecture comes from its structure. Our agentic
system needed nine to ten times as many messages per resident delivered as the
baseline, about 800\,000 tokens per run, and 1.8 to 2.7 times the wall-clock
budget of the compressed clock. 140 of its 150 novel runs finished over
budget (Section~\ref{sec:res:responsetime}). A designer should plan this cost
from the start and decide what it has to buy. Other work finds that one
strong agent with good prompts can match a multi-agent discussion
\parencite{wang2024}. On our scenarios it bought
nothing, because no scenario required adaptation. Whether it pays off on a
scenario that passes Gate~0 is untested.

These considerations come from one evaluation of one architecture on one
case. The case covers one facility, one city, one hazard and one time scale.
The residents are a passive count, and the population is homogeneous, so the
considerations say nothing about equity. They are a starting point for the
next design in this space and should be tested there before they are
generalised.
