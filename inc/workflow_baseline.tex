This chapter describes the control condition of the study, the workflow
baseline. It is a single scripted Incident Commander (IC) that runs the same
evacuation as the agentic system. It sees the same scenarios, may use the same
commands and writes to the same event log. Only the way it decides is
different. The IC follows a written command doctrine step by step, and no
language model takes part in its coordination decisions.

A weak control would prove nothing, so we built the baseline on an established
emergency command doctrine. We froze it before the novel disruptions were
revealed. The baseline scored the highest survival level on every disruption
tested (Chapter~\ref{ch:results}). Section~\ref{sec:crit:gate0} discusses what
this win does and does not show.

\section{Design}
\label{sec:wf:rationale}

The baseline is a plain Python program without a workflow engine such as
Camunda or Temporal, which would add a second place where the two systems
could differ. The IC runs on the same engine as the ten agents
(Section~\ref{sec:ag:engine}). It replaces one step only, the step in which an
agent would call its language model. We call this step the seam. Everything
after the seam is the agentic side's own code.

The IC takes over the two coordination agents that reason with a model, the
command post (BIS) and the transport dispatcher (Hochbahn). Both conditions
share all other agents unchanged. A bus driver still drives and still uses a
language model to plan the route, because driving from A to B is the same act
under either architecture.

The doctrine is the German service regulation DV~100, \emph{Command and Control
in Operations} (\emph{Führung und Leitung im Einsatz}), under which the Hamburg
fire service works~\cite{fwdv100}. The code follows its elements one by one.
The American Incident Command System (ICS) is the scholarly anchor, because it
has a peer-reviewed research base~\cite{fema2017}. Where DV~100 gives too little
detail, we borrowed from ICS. In DV~100 terms, a multi-agency evacuation of 100
residents is a level C or D incident, which calls for one commander with a
staff~\cite[23]{fwdv100}. Central command is therefore the textbook form for
this case (Section~\ref{sec:bg:workflow}). The IC implements three of the staff
functions~\cite[13--14]{fwdv100}. The situation function (S2) keeps the
situation picture. The operations function (S3) plans the mission and chooses
the next phase. The logistics function (S4) turns a decision into transport,
escort and medical orders.

\section{The Command Cycle}
\label{sec:wf:cycle}

DV~100 describes command as a repeating cycle, the command process
(\emph{Führungsvorgang}), with three stages: situation assessment, planning and
issuing orders~\cite[24--25]{fwdv100}. Control comes from repeating the
situation assessment, which checks whether the orders are still
right~\cite[24]{fwdv100}. In the baseline, one turn of this cycle runs for
every wake, that is, for every scenario event or reply from another agent.

The seam is the planning stage. Three checks run there, one after the other
(Figure~\ref{fig:wf:cycle}).
\begin{enumerate}
  \item \textbf{Contingency check.} If an anticipated disruption has made the
  committed plan wrong, the IC issues a corrective order and stops
  (Section~\ref{sec:wf:disruptions}).
  \item \textbf{Fallback check.} If a report does not fit any known message,
  or a reply is overdue, the IC issues a holding order and stops
  (Section~\ref{sec:wf:fallback}).
  \item \textbf{Phase ladder.} Only if the plan still fits and the situation
  is understood does the IC choose the next phase of the mission.
\end{enumerate}
The order follows the doctrine. The IC does not push a plan forward when it
knows the plan is wrong or does not understand the situation. A correction
written for the case comes before a general hold. The resulting orders then
pass through the agentic engine's own code for checking, committing and
messaging. A parity test checks that these are the very same functions the
agents run, and not copies.

\paragraph{The phase ladder.}\label{sec:wf:steps} The mission has four phases.
Each has a time budget in simulated minutes and a condition that must hold
before it can start (Table~\ref{tab:wf:phases}). DV~100 leaves the phases of a
particular mission to the user, so we designed them ourselves. The operations
function chooses the phase from the situation picture alone, so the same
situation always leads to the same decision. It also computes the allocation
of residents to shelters again on every pass, so a correction reaches the
schedule without an extra branch.

\paragraph{How the fleet is used.}\label{sec:wf:fleet} Every scenario declares
two buses of 50 seats and marks the second as a reserve. The baseline's run
schedule does not read that mark. It gives each run to the bus that is free
first, so both buses leave at the start. The agentic transport agent keeps the
reserve parked by default. We treat the reserve role as soft. Both sides have
the same fleet and both may send bus~2, so sending it at once and keeping it
parked are two choices over the same capability. We therefore count this as a
difference in decisions, and it explains part of the survival gap.

\section{Handling Disruptions}
\label{sec:wf:disruptions}

\subsection{Anticipated Disruptions}

Three disruptions were known while we built the baseline, and the IC has a
prepared branch for each. In workflow terms these are anticipated exceptions,
with a handler written at build time~\cite{reichert2012}.
\begin{itemize}
  \item \textbf{Road closure.} The IC drops the shelter it can no longer reach
  and runs the allocation again over the shelters that remain.
  \item \textbf{Shelter capacity lost.} The IC runs the allocation again
  against the smaller capacity.
  \item \textbf{Bus breakdown.} The IC schedules the remaining runs over the
  buses it still has.
\end{itemize}
Each branch compares the target (\emph{Soll}), which is the order the IC has
committed, with the actual state (\emph{Ist}), which is the current situation
picture. The branch fires when the two do not match, and clears itself once
the correction makes them match again.

The IC has no routing command, because routing belongs to the transport side
and the drivers. It therefore answers a road closure over destinations. In the
evaluated road-closure scenario this lowers what the baseline can deliver to
60 of the 100 residents (Section~\ref{sec:cs:disruptions}). All 20 baseline
runs on the anticipated arm, 10 on each of the two scenarios, scored
$S = 1.000$. On the road closure that score is measured against the reduced
ceiling of 60, so the share of the full 100 residents is 0.60.
% source: ADR-0002 status note 2026-09-21; RESULTS sec.3. Verified by the
% author 2026-09-29 in scores.jsonl.

\subsection{Novel Disruptions: the Generic Fallback}
\label{sec:wf:fallback}

A novel disruption has no prepared branch. The baseline must not answer it
with a fresh plan, because that ability belongs to the treatment condition.
FwDV~100 requires a report back when the situation no longer matches the
order~\cite[37]{fwdv100}. It does not describe a holding order. We chose one
because it is the most careful response that needs no new plan. Two cases
trigger it, and neither names a particular disruption.
\begin{itemize}
  \item \textbf{A report outside the catalogue.} A message arrives whose type
  the IC does not expect and no contingency branch handles.
  \item \textbf{An overdue reply.} A decision waits for a reply, and its time
  budget has run out.
\end{itemize}
In both cases the IC reports to ZKD, tells the Augustinum to hold the
residents, and sends a hold-departure advisory to the transport dispatcher.
The IC itself took over Hochbahn, so this advisory lands in its own mailbox and
reaches no driver. The hold stops new orders, but a bus already on the road
keeps going. We wrote the fallback before any novel disruption existed. A test
reads its source code and fails if it names any message type, so it cannot
hold special cases for particular disruptions.

\section{The Execution Model}
\label{sec:wf:world}

A scripted scenario can only test a decision if the outcome depends on the
orders. If the scenario file said which shelter received how many residents, an
IC that sent everyone to a closed shelter would score as well as one that
planned around the closure. The execution model prevents this. It is a shared
module that plays the physical world and makes no decisions of its own. It
reads the dispatch orders the IC commits, drives them over the real road
distance, and reports what each shelter admitted. Three rules keep a wrong
plan from scoring well.
\begin{itemize}
  \item \textbf{A run lands only if it is still under way.} A bus that was
  recalled on the way delivers nobody.
  \item \textbf{A closed or full shelter admits nobody.} The residents who
  were turned away do not go back into the pool.
  \item \textbf{Nobody boards after the flood arrives.} The flood reaches the
  zone at 12:00, and the scorer applies the same limit.
\end{itemize}
Only the baseline's scenario files declare such a world. The agentic scenarios
reach the same effect through live agents. This difference works against the
baseline. Without a declared world, the baseline would receive its drop-off
confirmations from the script, whatever it had ordered, and the agentic side
never had that help. The world therefore cannot explain a baseline win. If it
had any effect, it made the baseline's margin look smaller. The argument holds
because the baseline won (Section~\ref{sec:crit:limitations}).

\section{Freeze and Determinism}
\label{sec:wf:freeze}
\label{sec:wf:cli}

We tagged the baseline in git as commit \texttt{67a14f8} on 2026-09-10, before
the novel scenarios arrived (Section~\ref{sec:eval:firewall}). One later change
(\texttt{e9e20cd}) added a switch that turns re-planning off for the no-replan
control (Section~\ref{sec:eval:noreplan}). It does not change what the doctrine
does, and the pre-registration discloses it in Amendment~6.

The baseline starts from a small command-line tool and reads the same scenario
files as the agentic side. Its decision path has no randomness, no model and
no network, so a run depends on its scenario file alone. The baseline writes the same decision rows as the agents, with token
counts and latency recorded as zero.

\section{What the Baseline Cannot Do}
\label{sec:wf:limits}

The limits of the baseline follow from what pre-scripted branching is
(Section~\ref{sec:bg:workflow}). An unanticipated disruption has no handler,
and the IC cannot write itself a new plan at run time. The structure adds one
more limit.
Because the IC merges BIS and Hochbahn into one node, the link between them
disappears, and with it four commands that only made sense on that link. The
agentic system can negotiate a deadline extension. The baseline cannot, because
under central command there is nobody to negotiate with. In return, the
baseline is fast, costs nothing to run, and every decision can be traced to a
written rule.

\paragraph{What this means for reading the results.} The original design
expected the baseline to be at its weakest on novel disruptions, where only the
holding order is left. The evaluation did not test that expectation. On all
five novel scenarios the baseline scored $S = 1.000$, and it drove the same
60.63 bus-kilometres as on the undisrupted run. A controller that ignores every
disruption commits the same orders and gets the same score. The baseline's
score is therefore the score of doing nothing different. It does not show that
the baseline adapted, and it does not show that it could not have.
Section~\ref{sec:crit:gate0} draws the consequence for the study.

\section{Chapter Summary}
\label{sec:wf:summary}

The workflow baseline is one scripted Incident Commander that follows the
DV~100 command cycle. It replaces the two coordination agents that use a model
and shares everything else with the agentic system. At the seam, it corrects a
plan that no longer fits, holds a situation it does not understand, and
otherwise moves up the phase ladder. An execution model makes the outcome
depend on the orders. Chapter~\ref{ch:data} describes the database that both
systems write to.
