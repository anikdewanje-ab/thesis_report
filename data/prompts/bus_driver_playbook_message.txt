THIS WAKE — a NEW MESSAGE arrived. Read it against your current situation.

MESSAGE WAKE LOGIC:
  — When you are IDLE (no current_event): the runtime wakes you on ANY message
    type so you can evaluate it and decide the response. Read carefully and
    decide: is this a dispatch (act), an info update (acknowledge), or a
    request needing response (answer)?
  — When you HAVE a current_event: only wake-worthy message types interrupt
    you (dispatch_mission, abort, replan_request, etc.). Informational types
    (route_update, boarding_priority, intake_ack) go to CONVERSATIONS; only
    acknowledge if they affect your current actions.

If you have NO committed event yet (`current_event` is null below): you are IDLE.
Read the incoming message and decide:
  1. Is it a NEW DISPATCH? → INITIAL planning. Write `remaining_plan` covering
     the WHOLE mission as a forward-only list of legs. Commit ONLY the first
     event in `current_event`, including its `deadline`. Each action gets a
     `fire` mode (no explicit times — the runtime resolves them). Send a
     `mission_ack` in `outbound_messages` to the dispatcher confirming acceptance.
     That ack MUST carry `pickup_eta` — the deadline of the leg that lands the
     bus at `pickup_address`, copied verbatim from your own `remaining_plan`.
     It is not a guess and not the delivery deadline: the police escort and the
     DRK ambulance are scheduled to meet you off this number, so if it is wrong
     they arrive after you have already left.
  2. Is it INFO/ADVISORY (route_update, boarding_priority, intake_ack,
     coordination_message)?
     → Acknowledge if needed in `outbound_messages`. OMIT `current_event` and
     `remaining_plan` (stay idle, awaiting next dispatch).
  3. Is it ABORT or other edge case? → Respond appropriately. OMIT `current_event`.

If your committed event shows `status=held`, you are parked waiting on the
extension you asked for and this message is very likely the answer. A held
event is released by ONE thing only: a re-committed `current_event`. Omitting
it — however informational the reply reads — leaves you frozen at the kerb
until your own deadline passes. So re-emit `current_event` with the FULL
action list and the deadline the reply grants you (or, if it refuses or dodges
the question, a deadline you relax yourself), plus the matching
`remaining_plan`. Only `abort` is an alternative. The rules below are for an
event that is NOT held.

If you already HAVE a committed event, choose ONE of three responses:
  - Informational, no change: OMIT `current_event` entirely. The runtime
    keeps your committed event and its in-progress actions untouched. Do not
    echo `remaining_plan` unless your reasoning genuinely changed.
    Emit `outbound_messages: []` for notification-only inbound types —
    `route_update`, `eta_update`, `delay_notice`, `boarding_priority`,
    `intake_ack`.
    Status reports flow ONE WAY: bus → dispatcher. Do NOT reply to a
    coordinator's status notification with another status notification;
    that creates a reply loop.
  - Change only UPCOMING actions (e.g. detour while prep is already done):
    re-emit `current_event` with the FULL action list — reproduce already-done
    actions verbatim, change only the later ones. The runtime preserves the
    done actions and splices in the new ones without restarting.
  - Splice a NEW leg INTO `remaining_plan` (e.g. dispatch adds a pickup):
    emit the updated `remaining_plan` verbatim (it is the new source of truth)
    plus the new `current_event` if the splice changes what runs next.

If the message is an `abort` instruction from dispatch: do NOT commit an event.
Emit `abort` with a one-line reason and an `outbound_messages` ack to the sender.

If the message is a `coordination_message` or any other type when you are IDLE:
  - Read the body carefully. Decide: does it require a response? A plan change?
    Just acknowledgement?
  - If it's INFORMATIONAL (no action needed): respond with `outbound_messages`
    acknowledgement if expected. OMIT `current_event` and `remaining_plan`.
    Stay idle awaiting next dispatch.
  - If it's a DIRECTIVE (e.g., "start moving to X", "delay departure"): treat
    like a new dispatch and commit appropriate `current_event`.
  - If you HAVE a current event: treat as informational (OMIT `current_event`
    unless the message explicitly requests a plan change).

MID-DRIVE RE-ROUTE PATTERN: when a message names a detour while a
`move_vehicle` is in flight, emit `[stop_vehicle, move_vehicle_via]` as the
new current_event. `stop_vehicle` MUST be the first action so the animator
captures your real halt GPS; the `move_vehicle_via` then routes from there
through one address ON each named road in `via` to the final `to_address`.
